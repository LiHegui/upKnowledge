Q: WebRTC 是什么？1 对 1 连接的完整建立流程是怎样的？ ​

查看答案

A:

一、定义 ​

WebRTC（Web Real-Time Communication）是网页实时通信的 W3C/IETF 标准，核心模式是 **P2P（点对点）**通信 —— 浏览器与浏览器（或原生客户端）之间直接建立传输通道，媒体流不经过服务器中转。

并且 WebRTC 默认强制加密，无法关闭：

传输内容加密协议底层协议
音视频流SRTPUDP（RTP）
密钥协商DTLSUDP
业务数据DTLSSCTP

二、1 对 1 建连的完整流程 ​

🔑 核心认知：信令交换（SDP） 与 ICE 网络协商 是并行发生的，不是串行的两个阶段。

第一步：媒体协商（SDP 交换） ​

SDP（Session Description Protocol）描述的是媒体能力 —— 支持哪些编解码器、分辨率、码率、传输方向等。

以 A 呼叫 B 为例：

顺序端动作
1AcreateOffer() 生成 Offer（声明自己的媒体能力）
2AsetLocalDescription(offer) 保存本地描述
3A → B通过信令服务器（如 WebSocket）把 Offer 发给 B
4BsetRemoteDescription(offer) 保存 A 的能力
5BcreateAnswer() 生成 Answer（取双方能力交集）
6BsetLocalDescription(answer) 保存
7B → A通过信令回传 Answer
8AsetRemoteDescription(answer) 保存

至此媒体能力握手完成。

js
// ────────── A 端（发起方 / Caller）──────────
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com:3478', username: 'user', credential: 'pass' },
  ],
})

// 本地流加入连接（addTrack 会影响 SDP 内容，必须在 createOffer 之前）
stream.getTracks().forEach(track => pc.addTrack(track, stream))

// ⚠️ 候选是「逐条冒出来」的，边收集边发送 —— 这就是 Trickle ICE
pc.onicecandidate = (e) => {
  if (e.candidate) {
    signaling.send({ type: 'candidate', candidate: e.candidate })
  } else {
    // e.candidate === null 表示候选收集结束（End-of-candidates）
  }
}

pc.ontrack = (e) => { remoteVideo.srcObject = e.streams[0] }

const offer = await pc.createOffer()
await pc.setLocalDescription(offer)   // ← ICE 候选收集由这一步触发（见下方注意）
signaling.send({ type: 'offer', sdp: offer })

// 收到 Answer
signaling.on('answer', async ({ sdp }) => {
  await pc.setRemoteDescription(sdp)
})
// 收到对端候选（可能在 Answer 之前就到达）
signaling.on('candidate', async ({ candidate }) => {
  await pc.addIceCandidate(candidate)
})

第二步：网络协商（ICE 候选交换） ​

关键点：ICE 候选的收集不是等 SDP 交换完才开始的，它与信令交换交错并行进行。

⚠️ 精确的触发时机：new RTCPeerConnection() 时只是解析并保存 iceServers 配置，真正的候选收集（gathering）由 setLocalDescription() 触发 —— 此时 iceGatheringState 从 new → gathering → complete。

所以准确的说法是：A 调用 setLocalDescription(offer) 的那一刻就开始异步收集候选，完全不等 B 的 Answer 回来。这才是"并行"的真正含义，也是面试官爱抠的细节。

ICE 代理向 STUN / TURN 服务器收集三类候选地址：

候选类型缩写含义优先级说明
Hosthost本机内网 IP最高同一局域网可直连，0 成本
Server ReflexivesrflxSTUN 探测到的公网映射地址中NAT 打洞的主力，约 80% 场景可打通
RelayrelayTURN 服务器中继地址最低✅ 兜底，❌ 消耗服务器带宽（流量走服务器）

双方通过 onicecandidate 事件，逐条把生成的候选经信令服务器双向发给对方（A→B、B→A 都要发）—— 这就是 Trickle ICE：不等全部收集完再一次性发（那叫 Vanilla ICE，建连慢得多）。

第三步：连通性检查与提名（ICE Nomination） ​

  1. 配对：双方把本地候选与远端候选两两配对成 Candidate Pairs
  2. 探测：对每个 pair 互发 STUN Binding Request，做双向连通性检查
  3. 提名：ICE 框架按响应速度与优先级，从所有可用 pair 中**提名（Nomination）**出最优的一对路径
  4. 加密：最优路径打通后 → DTLS 握手交换密钥 → SRTP 加密传输音视频

💡 信令服务器全程只交换元数据（SDP + ICE 候选）。一旦 P2P 建立，媒体流不再经过它 —— 这是 WebRTC 节省服务器带宽的根本原因。

但注意：信令服务器不可省略。两端在建连前无法互相通信，必须有第三方帮它们"交换名片"。

三、数据传输：RTCDataChannel ​

传输文件、文本、信令、游戏状态等非音视频数据，用 RTCDataChannel：

js
const dc = pc.createDataChannel('file', {
  ordered: false,        // 是否保证顺序
  maxRetransmits: 0,     // 最大重传次数（配 0 ≈ UDP 语义）
  // maxPacketLifeTime: 300,  // 或按时间约束（二者互斥）
})
dc.onopen = () => dc.send('hello')
dc.onmessage = (e) => console.log(e.data)

它基于 SCTP 协议，可靠性可配置：

模式配置语义适用场景
Reliable（默认）不配 maxRetransmits / maxPacketLifeTime有序 + 必达，类似 TCP文件传输、聊天消息
Partial Reliable配 maxRetransmits 或 maxPacketLifeTime可丢包，类似 UDP游戏状态同步、实时位置

⚠️ 区分陷阱：音视频走 SRTP，DataChannel 走 SCTP，两者相互独立、互不依赖 —— 可以只用 DataChannel 不开摄像头（纯 P2P 文件传输就是这么做的）。

四、追问：人数超过 2 个怎么办？（架构演进） ​

2 人通话 P2P 直连（Mesh）完全够用。但 3 人以上绝对不能继续两两直连 —— 每个客户端要同时上传 N-1 路、下载 N-1 路，带宽与 CPU 呈平方级增长（整体连接数 N(N-1)/2）。

生产环境必须引入服务端转发：

架构上行 / 下行服务器开销画质适用规模
Mesh（P2P 全互联）N-1 / N-1零（无服务器）原画≤ 3 人
SFU（选择性转发）1 / N-1低（只转发，不编解码）✅ 原画主流方案，几十人
MCU（混流）1 / 1高（解码 + 混流 + 再编码）❌ 有损弱端设备、录制、直播推流

SFU（Selective Forwarding Unit） 的核心：

  • 每个客户端只与 SFU 建立一个 PeerConnection
  • SFU 收到流后不解码、不混流，只按订阅关系原封转发
  • 20 人会议：每端只上传 1 路，下行按需接收 → 浏览器轻松扛住

配合 Simulcast（联播 / 分层编码）：发送端同时推高 / 中 / 低三档清晰度，SFU 根据每个接收端的实时网络状况动态选择转发哪一层，实现弱网下的流畅度优化。

js
// Simulcast：在 addTransceiver 时声明三档编码
pc.addTransceiver(videoTrack, {
  direction: 'sendonly',
  sendEncodings: [
    { rid: 'h', maxBitrate: 1_200_000 },
    { rid: 'm', maxBitrate: 400_000, scaleResolutionDownBy: 2 },
    { rid: 'l', maxBitrate: 150_000, scaleResolutionDownBy: 4 },
  ],
})

业界常用开源 SFU：mediasoup、Janus、LiveKit、ion-sfu。

五、追问：WiFi 切 4G 或网络闪断怎么办？ ​

绝对不能粗暴销毁 PeerConnection 重建（要重走全套 SDP 协商 + 重新采集设备，用户会看到黑屏几秒）。WebRTC 原生提供了 ICE Restart 优雅重启机制。

1. 精准检测：分清两种状态 ​

状态监控层级什么时候变化排查用途
iceConnectionState网络层（ICE 候选对连通性）WiFi 信号弱、网络切换时先变 disconnected✅ 重连的首要判断指标
connectionState聚合层（ICE + DTLS 整体状态）任一子传输失败即变化；证书 / 密钥协商失败直接 failed区分"网络不通"还是"加密握手失败"

⚠️ 排查顺序：先看 iceConnectionState；若已 failed，再看 connectionState 是否同步异常 —— 以此区分网络路径断了还是证书 / DTLS 失效。

补充：connectionState 不是"只监控 DTLS"，它是 iceConnectionState 与各 DTLSTransport 状态的聚合值，任意一个 transport 失败都会拉低它。

2. 状态机处理原则 ​

js
pc.oniceconnectionstatechange = () => {
  switch (pc.iceConnectionState) {
    case 'disconnected':
      // 网络闪断 / 切网 —— ❌ 不要报错、不要销毁，启动重连计时器
      scheduleIceRestart()
      break
    case 'failed':
      // ✅ 此时才是真正连不上，通知用户网络异常
      notifyUser('网络异常')
      break
    case 'connected':
    case 'completed':
      resetBackoff()   // 恢复成功，重置退避计数
      break
  }
}
状态含义正确处理
disconnected网络闪断 / 切换，可能自愈启动重连计时器，不报错
failed所有候选对都不通通知用户网络异常 + ICE Restart

3. 优雅恢复：ICE Restart ​

js
// 只有 Offer 发起方（或约定的一方）执行，避免双方同时 restart 造成协商冲突
const offer = await pc.createOffer({ iceRestart: true })
await pc.setLocalDescription(offer)
signaling.send({ type: 'offer', sdp: offer })

iceRestart: true 会强制生成新的 ICE 账号（ufrag）与密码（pwd），让两端丢弃旧的无效候选对，重新走 STUN 打洞流程。

✅ 关键优势：编解码器没变，媒体能力无需重新协商，只换网络路径 —— 重连速度远快于全新建连，且媒体轨道（track）保持不变，用户几乎无感。

4. 工程防坑：指数退避 ​

重连必须加指数退避（Exponential Backoff），绝不能每 100ms 疯狂重试，否则会把信令服务器打挂：

js
let retry = 0
function scheduleIceRestart() {
  const delay = Math.min(1000 * 2 ** retry++, 30_000)   // 1s → 2s → 4s … 上限 30s
  const jitter = Math.random() * 300                     // 加抖动，避免大量客户端同时重连造成惊群
  setTimeout(doIceRestart, delay + jitter)
}

💡 加 jitter（随机抖动）同样重要：一旦机房网络抖动导致上千客户端同时进入退避，整齐的 1s/2s/4s 会形成惊群效应，把信令服务器压出周期性尖峰。

六、总结陈词 ​

WebRTC 1 对 1 连接依赖 SDP 能力协商与 ICE 路径发现的并行机制，通过 setLocalDescription 与 onicecandidate 的紧密配合（Trickle ICE）完成建连，最终由 DTLS/SRTP 加密传输；多人场景必须采用 SFU 服务端转发（配合 Simulcast 应对弱网）；断连时依赖 ICE Restart 优雅重启加指数退避，保障用户无感恢复。

Q: 什么是微前端？实现方案、核心技术挑战与选型思路？ ​

查看答案

A:

一、先定性：什么是微前端 ​

微前端是一种把前端应用拆分为多个独立开发、独立部署、独立运行的小型应用的架构模式，由主应用（基座） 在运行时组合成一个整体。思想源自微服务：每个子应用可用不同技术栈，拥有独立的 CI/CD 流水线。

要落地微前端，必须解决 5 个核心问题：

核心问题要解决什么
JS 隔离子应用不污染主应用 / 其他子应用的全局变量
样式隔离子应用 CSS 不互相覆盖
路由管理主子路由如何协同、刷新不 404
应用间通信共享登录态、用户信息等
公共依赖React/Vue 等别重复加载 N 份

二、实现方案分类（按集成时机） ​

方案集成时机代表框架隔离程度性能
运行时集成运行时（浏览器）qiankun、micro-app、wujie高中
构建时集成构建时Module Federation低最高
服务端集成CDN 边缘ESI（Edge-Side Includes）高高（可缓存）
  • 运行时集成：主应用在浏览器端动态加载子应用资源。✅ 真正的独立部署，❌ 有运行时开销（沙箱、代理）
  • 构建时集成：通过构建工具共享模块。✅ 性能最好、无运行时负担，❌ 无内置隔离
  • 服务端集成：CDN 边缘节点拼装 HTML。适合内容型网站，❌ 不适合 SPA

早期还有 iframe 方案：隔离性天然满分，但弹窗无法覆盖全屏、路由无法同步、通信麻烦、白屏加载慢 —— 所以现代方案都在"绕开 iframe 的缺点，保留它的隔离能力"。wujie 的思路正是让 iframe 只跑 JS，DOM 渲染到主应用。

三、三大运行时框架对比 ​

维度qiankun（蚂蚁）micro-app（京东）wujie（腾讯）
技术基础single-spa + import-html-entryWeb ComponentsWeb Components + iframe
JS 隔离Proxy / Snapshot 沙箱Proxy 沙箱iframe 沙箱（最强）
子应用改造成本较高（需暴露生命周期）最低（类似用标签）低
组件级使用❌✅✅
成熟度 / 生态✅ 最成熟中中
  • qiankun：基于 single-spa，子应用需导出 bootstrap / mount / unmount 三个生命周期，并配置 library + umd 打包。方案最成熟、坑最少、资料最全，中后台首选。
  • micro-app：把子应用封装成 <micro-app> 自定义元素，对子应用侵入性最低，支持组件级微前端。
  • wujie：Web Components 做容器 + iframe 做 JS 沙箱 + Proxy 做通信桥接。iframe 沙箱做到浏览器级隔离，同时 DOM 渲染到主应用保证交互体验（弹窗、全屏正常）。

选型思路：

场景推荐
中后台系统、要稳、团队多qiankun
子应用不想改代码 / 需要组件级嵌入micro-app
子应用不可控（第三方接入）、要求强隔离wujie
同技术栈、只想共享模块和依赖Module Federation

四、核心技术①：JS 沙箱 ​

目的：让子应用在独立的全局环境中运行，不污染真实 window。

方案一：Proxy 沙箱（qiankun / micro-app 主力）

js
// Proxy 沙箱核心逻辑（简化版）
class ProxySandbox {
  constructor() {
    const rawWindow = window
    const fakeWindow = Object.create(null)
    const proxy = new Proxy(fakeWindow, {
      // 写：只落到 fakeWindow，不碰真实 window
      set: (_, prop, value) => { fakeWindow[prop] = value; return true },
      // 读：优先 fakeWindow，取不到再回退真实 window
      get: (_, prop) => {
        if (prop === 'window' || prop === 'self' || prop === 'globalThis') return proxy
        return fakeWindow[prop] || rawWindow[prop]
      },
      has: (_, prop) => prop in fakeWindow || prop in rawWindow,
    })
    this.proxy = proxy
  }
}
// 子应用代码被 with(proxyWindow){...} 包裹执行，从而劫持全局访问

激活时创建、卸载时整体丢弃，天然实现多实例互不干扰。

方案二：Snapshot 沙箱（降级方案）

不支持 Proxy（IE）时用：激活前快照 window，卸载时逐个恢复并记录 diff。❌ 只能单实例，无法多子应用并存。

方案三：iframe 沙箱（wujie）

JS 丢进隐藏 iframe 执行，天然拥有独立 window / document，理论上 100% 隔离；代价是 DOM 需桥接回主应用。

方案隔离级别兼容性多实例典型框架
Proxy 沙箱高（99% 场景）好（IE ❌）✅qiankun、micro-app
Snapshot 沙箱中（可能有残留）极好❌qiankun 降级
iframe 沙箱极高（浏览器级）极好✅wujie

⚠️ Proxy 沙箱的边界（加分点）：它只能代理全局变量访问，管不住副作用。所以 qiankun 还额外 patch 了 setTimeout / setInterval / addEventListener / 动态 <script> <style> 插入 —— 卸载时统一清理定时器与监听，防止残留。但 document.body 直接操作、原型链污染等仍可绕过。iframe 沙箱是理论上唯一能完全隔离的方案。

五、核心技术②：样式隔离 ​

方案隔离效果运行时开销推荐度
CSS Modules / CSS-in-JS高无✅ 首选（构建时哈希类名）
动态样式管理中低✅ 兜底（挂载追加、卸载移除）
PostCSS 自动 scoping高无✅ 推荐（自动加 [data-app-id]）
Shadow DOM极高低⚠️ 弹窗逃逸问题
css
/* CSS Modules：构建前 */  .header { color: red; }
/* 构建后 */              ._header_1a2b3 { color: red; }

⚠️ Shadow DOM 的坑：Element Plus / antd 这类组件库的弹窗（Modal / Message）默认挂到 document.body，会逃逸出 Shadow 边界导致样式全丢，必须改 getPopupContainer / teleport 目标。

💡 qiankun 的 experimentalStyleIsolation: true 会自动给子应用选择器加 div[data-qiankun="app1"] 前缀 —— 本质就是运行时版 PostCSS scoping，但对 @media、:root 等有边界。

最佳实践（组合拳）：CSS Modules（设计时根治）+ 动态样式管理（运行时兜底）+ 团队命名约定（BEM 前缀）。

六、核心技术③：路由管理 ​

用户访问 /app1/orders 的完整链路：

1. 主应用 activeRule: '/app1'  → 命中 → 加载并激活子应用
2. 子应用收到 baseroute = '/app1'
3. 子应用内部路由 '/orders'   → 拼成完整路径 '/app1/orders'
4. 子应用渲染订单页
js
// 子应用路由 base 必须区分「独立运行」与「被基座接管」
const router = createRouter({
  history: createWebHistory(window.__POWERED_BY_QIANKUN__ ? '/app1' : '/'),
  routes: [/* ... */],
})

⚠️ 最高频的坑：子应用路由刷新 404。原因是 history 模式下服务器没有该物理路径，必须配 SPA 回退：

nginx
location /app1 { try_files $uri $uri/ /app1/index.html; }

另一个坑：子应用静态资源 404 —— 需要设置 __webpack_public_path__ 或 webpack output.publicPath 为子应用的绝对地址。

七、核心技术④：应用间通信 ​

js
// 方案一：Custom Events（框架无关，最通用）
window.addEventListener('app-event', (e) => console.log(e.detail))
window.dispatchEvent(new CustomEvent('app-event', { detail: { type: 'orderPlaced' } }))
js
// 方案二：框架内置（qiankun 全局状态）
// 主应用
const actions = initGlobalState({ user: { id: 123 } })
actions.setGlobalState({ user: { id: 456 } })
// 子应用
export function mount(props) {
  props.onGlobalStateChange((state, prev) => { /* 响应变化 */ })
}
框架内置通信方式
qiankuninitGlobalState → setGlobalState / onGlobalStateChange
micro-appdata 属性 + window.microApp API
wujiewindow.$wujie bus / props

💡 原则：通信应尽量少。 频繁通信 = 耦合过深 = 这两个模块本来就不该拆。这句话是面试里体现架构判断力的关键。

八、核心技术⑤：公共依赖 ​

微前端既要隔离（互不污染），又要共享（依赖别加载 N 份），二者天然冲突。所有共享策略的本质，都是在「隔离」与「共享」之间找平衡。

先分清两种形态，策略重点完全不同：

形态例子策略重点
公共第三方依赖React、Vue、Element Plus、lodash解决「加载几份」（体积去重）
自研公共能力业务组件库、登录态、权限、axios 封装解决「怎么共享又不耦合」
策略做法评价
各自打包每个子应用 npm install 各打一份❌ 页面加载 N 份 React，体积爆炸、版本漂移
CDN + externals主应用 CDN 引入，子应用 externals 排除✅ 全站只加载一次，❌ 版本被锁死、子应用无法独立升级
Module Federation shared构建时协商，singleton + requiredVersion✅ 自动去重 + 版本兜底，当前最优解

九、Module Federation（Webpack 5 / Rspack） ​

MF 不追求隔离，追求共享 —— 这是它与 qiankun 等的根本分野。

核心能力：Remote exposes 暴露模块 → Host remotes 消费模块 → shared 单例共享依赖。

js
// Remote（子应用）
new ModuleFederationPlugin({
  name: 'app1',
  filename: 'remoteEntry.js',
  exposes: { './OrderList': './src/views/OrderList' },
  shared: { react: { singleton: true, requiredVersion: '^18.0.0' } },
})
// Host（主应用）
new ModuleFederationPlugin({
  remotes: { app1: 'app1@https://cdn.example.com/app1/remoteEntry.js' },
  shared: { react: { singleton: true } },
})

✅ 无沙箱开销、无运行时钩子，性能最好；shared 保证第三方库只加载一次。 ❌ 无 JS / CSS 隔离，且要求构建工具与版本对齐（跨技术栈困难）。

💡 生产最佳实践（加分项）：两者不是二选一 —— 用运行时框架（qiankun/wujie）处理应用级隔离与路由，用 Module Federation 处理模块级共享（共享组件库、工具函数）。

十、收尾：什么时候用、什么时候不用 ​

✅ 适合用❌ 不适合用
多团队独立开发、独立部署不同模块小团队或简单应用
大型中后台（CRM、ERP、低代码平台）对首屏性能有极致要求
渐进式技术栈迁移（Vue2 → Vue3、jQuery → React）团队缺乏基建 / 运维能力
代码库过于庞大，构建慢到不可接受拆分后模块间需频繁通信

三个原则：

  1. 拆分要有边界 —— 频繁通信说明不该拆
  2. 先有痛点再上方案 —— 不要为了架构而架构
  3. 架构是渐进的 —— 从单体自然演进，而非一开始就上微前端

微前端的核心价值：让大型前端团队能像后端微服务团队一样，独立开发、独立部署、各自演进。 如果它不能带来这些好处，微前端就只是增加了系统复杂度的累赘。

Q: 微前端里的公共组件怎么做？技术栈不一样的子应用之间也能共享组件吗？ ​

查看答案

A:

先给结论：公共组件不能一刀切，要按「组件对框架运行时的依赖有多深」分层处理。跨技术栈共享能做，但只在浅层能做 —— 越接近浏览器原生的越能共享，越依赖框架特性（响应式、Hooks、插槽、指令）的越不能。

组件类型同栈方案跨栈能否共享
纯逻辑（utils / request / 埋点 / 权限判断）npm 包✅ 完全可以，本来就与框架无关
设计层（Design Token / CSS 变量 / 样式规范）npm 包✅ 完全可以，且性价比最高
原子 UI（Button / Icon / Upload / Picker）npm 组件库✅ 可以，靠 Web Components
复杂业务模块（审批流、选人器、附件预览）npm 组件库⚠️ 别硬做，退化成微组件子应用
框架强绑定（v-model 指令、带 Hooks 状态的容器组件）npm 组件库❌ 做不到，只能各栈实现一遍

一、同栈共享：npm 包 → Monorepo → Module Federation 三级演进 ​

第一级：私有 npm 包（起点）

bash
@company/ui        # 组件库
@company/utils     # 纯逻辑
@company/request   # 统一请求封装 + 拦截器
  • 优点：开发体验和普通项目完全一致，版本可控、可回滚
  • 缺点：改一次要各子应用逐个升级发版，容易出现版本漂移

第二级：由此引出 Monorepo（解决"共享代码的开发体验"）

npm 包真正的痛点不在"共享"，而在改动链路太长：改组件库 → build → 发版 → 各子应用 npm update → 各自提 PR。改一行文案要走五步，跨五个仓库。

Monorepo 就是对这个痛点的回答：一个 Git 仓库里放多个独立可发布的包与应用，用 workspace 把它们连成一张依赖图。

repo/
├── apps/                  # 各个可独立部署的应用
│   ├── main/              # 主应用（基座）
│   ├── app-order/         # 子应用：订单
│   └── app-user/          # 子应用：用户
├── packages/              # 共享包
│   ├── ui/                # 组件库
│   ├── utils/             # 纯逻辑
│   └── request/           # 请求封装
└── pnpm-workspace.yaml
json
// apps/app-order/package.json —— 依赖的不是版本号，而是「工作区里的那个包」
{ "dependencies": { "@company/ui": "workspace:*" } }

workspace:* 让 pnpm 把 packages/ui 软链进 node_modules，于是：改组件库源码 → 子应用热更新立即生效，不用 build、不用发版；跨应用的改动能在一次 PR 里原子提交，版本永不漂移。工具链上再配 Turborepo / Nx，靠依赖图做增量构建和缓存，只重建"受影响的包"。

💡 深刻之处：Monorepo ≠ Monolith（单体）。

判断是不是单体，看的是能否独立构建、独立部署，而不是有几个 Git 仓库。Monorepo 管的是代码怎么放（开发期），微前端管的是运行时怎么拆（部署期），两者完全正交，且天生互补：

微前端把「运行时」拆开求独立，Monorepo 把「代码库」合起来求一致 —— 合在一起才是「独立部署 + 统一基建」。这也是当下中后台的主流形态：Monorepo 管代码 + 微前端管运行时 + Module Federation 管模块共享。

⚠️ 注意：Monorepo 的代价也很实在 —— 仓库体积膨胀（clone 慢，需 shallow / sparse checkout）、CI 必须做 affected 增量（否则改一行全量构建）、权限无法按仓库切分（靠 CODEOWNERS 缓解）。最隐蔽的一条：物理边界消失后，"顺手跨包 import" 会悄悄把模块耦合回单体，边界只能靠依赖规则（如 ESLint no-restricted-imports、Nx tags）来强约束。

第三级：Module Federation（要"改一次线上全部生效"）

Monorepo 解决的是开发期即时生效，但产物仍是各应用各自打包 —— 组件库改动上线，各子应用还是要重新构建部署一遍。要做到"组件库单独发布、线上运行时立即生效"，就得上 MF：shared 里 singleton: true 保证全局只有一份，组件从 Host 运行时拉取。

⚠️ 注意：MF 的前置条件是框架与版本一致（requiredVersion 对不上会退化成各自加载一份），所以它属于同栈方案，跨栈用不了。

二、跨技术栈到底能不能共享组件？ ​

能，但要先想清楚共享的是什么。 判据只有一条：这个组件对框架运行时的依赖有多深。

① 纯逻辑 —— 无损共享

请求封装、日期处理、埋点、权限判断、表单校验规则，本质是纯函数，跟框架毫无关系，一个 npm 包搞定，这一层永远该共享。

② 设计层 —— 最容易被忽略，但性价比最高

跨栈场景下用户真正感知到的"不是一个系统"，是视觉和交互不一致，而不是"你们没复用代码"。所以更划算的做法是共享设计而不是共享实现：

css
/* @company/design-tokens —— 一份 CSS 变量，Vue / React / Angular 全都能吃 */
:root {
  --c-primary: #1677ff;
  --c-danger:  #ff4d4f;
  --radius-md: 6px;
  --space-md:  16px;
  --font-size-base: 14px;
}

各栈的 Button 可以各写一遍，但只要都消费同一套 Token，视觉就是统一的；换肤时改一处，所有子应用（包括 Shadow DOM 内部）同步生效。

💡 深刻之处：跨栈共享的正确顺序是 Design Token → 纯逻辑 → 原子组件 → （尽量不要）业务组件。很多团队一上来就想跨栈复用组件代码，结果做出一堆难用的封装；而真正的目标"体验一致"，用一份 Token 加一份设计规范就解决了 80%。

③ 原子 UI —— 靠 Web Components

真要跨栈复用组件代码，唯一优雅解是回到浏览器原生标准：用 Vue3 的 defineCustomElement 或 Lit 写一次，Vue / React / Angular 都能当标签用。

js
// 组件库侧：Vue3 组件 → 自定义元素
import { defineCustomElement } from 'vue'
import UserPicker from './UserPicker.vue'

customElements.define('company-user-picker', defineCustomElement(UserPicker))
jsx
// React 子应用侧：当原生标签用
function Demo() {
  const ref = useRef(null)

  useEffect(() => {
    // ⚠️ 复杂对象必须用 property 赋值，不能走 attribute（attribute 只能传字符串）
    ref.current.options = [{ id: 1, name: '张三' }]

    // ⚠️ 自定义事件不走 React 合成事件系统，必须手动 addEventListener
    const onChange = (e) => console.log(e.detail)
    ref.current.addEventListener('change', onChange)
    return () => ref.current?.removeEventListener('change', onChange)
  }, [])

  return <company-user-picker ref={ref} placeholder="请选择" />
}

⚠️ 注意：Web Components 的四个必踩坑 ——

  1. 属性传值：attribute 只能是字符串，对象/数组必须用 property
  2. 事件：只能 CustomEvent + addEventListener，框架的 @change / onChange 不一定能捕获
  3. 样式：Shadow DOM 内外隔绝，主题必须靠 CSS 变量穿透（--primary-color），不能靠全局 class
  4. 表单：v-model / React 受控组件需要额外适配，复杂表单组件成本很高

这四条坑的共同原因是：WC 只有 DOM 这一层契约，框架给的语法糖（双向绑定、合成事件、插槽、样式作用域）全都要手写补回来。所以 WC 适合原子组件（图标、上传、选择器），不适合复杂业务组件 —— 适配成本会超过重写成本。

④ 复杂业务模块 —— 退化成"微组件"，用微前端解微前端

审批流配置器这种带路由、带状态、带一堆请求的模块，与其硬做成 WC，不如直接把它做成一个子应用，被其他子应用手动挂载到某个 DOM 节点（非路由驱动）：

js
import { loadMicroApp } from 'qiankun'

// 不注册路由，纯手动挂载到页面局部区域 —— 这就是「微组件」用法
const app = loadMicroApp({
  name: 'approval-widget',
  entry: '//localhost:7101',
  container: '#widget-slot',
  props: { bizId: 123 },
})

// 组件销毁时务必卸载，否则内存泄漏 + 事件残留
onUnmounted(() => app.unmount())
  • 优点：彻底跨栈，业务方零改造，内部想用什么框架都行
  • 缺点：粒度粗、有加载开销，只适合"大块、独立、低频交互"的模块

⑤ 框架强绑定组件 —— 承认做不到

依赖 v-model、自定义指令、Vue 响应式对象、React Hooks 状态的容器组件，跨栈没有办法共享，硬做只会做出一个既不像 Vue 也不像 React 的四不像。这一层的正确答案是：各栈实现一遍，但共用同一套 Design Token 和同一份组件行为规范。

⚠️ 注意：这也反过来说明 —— 多技术栈的代价大头就压在这一层。所以跨栈应该是"遗留系统迁移 / 外部团队接入"的逃生舱，而不是新项目主动选择的目标。

三、公共能力（登录态 / 主题 / 多语言）怎么统一？ ​

组件之外，通常紧接着会追问这三个，答法是同一个思路：主应用集中管理「状态」，子应用各自消费「状态」。

能力做法
登录态 / token主应用统一登录、刷新 token，通过 props + globalState 下发；子应用不自己存 token，避免多份过期不一致
主题换肤主应用在 :root 挂 CSS 变量，子应用只消费变量、不硬编码色值 —— 天然跨框架、跨 Shadow DOM
多语言 i18n主应用只管当前 locale 并下发；语言包由各子应用自带，避免主应用维护巨型 JSON
js
// 主应用：初始化全局状态
import { initGlobalState } from 'qiankun'

const actions = initGlobalState({ token: '', theme: 'dark', locale: 'zh-CN' })

// 子应用：监听并同步到自己的 i18n 实例
props.onGlobalStateChange(({ locale }) => {
  if (locale) i18n.global.locale.value = locale   // 语言包在子应用本地，只同步「当前语种」
}, true)

⚠️ 注意：globalState 只放轻量、全局、低频变更的数据（token、用户信息、主题、语种）。把业务数据甚至组件实例塞进去共享，会让子应用重新耦合成隐形单体 —— 通信越少，拆分越成功。

四、总结陈词 ​

公共组件我会按「对框架运行时的依赖深度」分层：

同栈是三级演进 —— npm 包起步，用 Monorepo 把组件库和各子应用放进一个仓库（改源码即时生效、跨应用改动一次 PR 原子提交），要做到线上运行时实时生效再上 Module Federation。顺带说一句：Monorepo 不是单体，微前端拆的是运行时、Monorepo 合的是代码库，一个求独立部署、一个求统一基建，两者正交互补。

跨栈能共享，但只在浅层能：纯逻辑和 Design Token 无损共享（而且这一层最划算 —— 用户要的是"体验一致"，不是"代码复用"），原子组件靠 Web Components 回到浏览器原生契约，复杂业务模块退化成微组件子应用，框架强绑定的那部分就承认做不到、各栈实现一遍。

而登录态、主题、多语言这类公共能力，一律主应用集中下发、子应用本地消费 —— 主应用管"是什么"，子应用管"怎么用"。
