大模型应用开发 · 从零系统学习计划（前端 · 冲刺版） ​

开始日期：2026-06-24 预计周期：3 周（冲刺） 每日时长：3 小时（每周约 5 天 → 周投入约 15 小时，3 周合计约 45 小时） 学习方式：概念吃透 → 当天动手 → 通过验收标准才算过 最终产出：一个完整的 AI 应用（前端 + 后端代理 + 流式 + 工具调用 + Agent），外加一套自己的 AI 编程工作流

怎么用这份计划 ​

这是一门从零开始的课，不依赖任何已有基础。六个模块层层递进，每个模块都有三段：

  • 🎯 学什么 —— 这一阶段必须搞懂的概念
  • 💻 动手 —— 当天就要敲的代码 / 实验
  • ✅ 验收标准 —— 能做到这几条，才算真的会了，再往下走

铁律：不要只看不练。每个概念学完当天就写代码验证。看懂 ≠ 会，能从空白文件写出来才算会。

模块一：LLM 与 API 调用（第 1 周 · 前半） ​

🎯 学什么 ​

  • 大模型到底是什么：它本质是"根据上文预测下一个 token"，不是数据库、不是搜索引擎
  • 三个必懂概念：Token（文本的计费/计量单位）、上下文窗口（一次能塞多少）、温度 temperature（随机性）
  • Chat 接口的核心结构：messages 数组 + 三种角色 system / user / assistant
  • 一次请求的生命周期：请求体 → 模型 → 响应体（含 usage 计费字段）
  • 前端铁律：API Key 绝对不能放在前端代码/浏览器里，必须经过自己的后端中转

💻 动手 ​

  1. 注册一个能用的模型服务（OpenAI / Claude / 通义千问 / DeepSeek 任选，国产的好上手）
  2. 用 curl 或 Node 的 fetch 直接发一次最原始的请求，不用任何 SDK，看清楚请求体和返回体长什么样
  3. 搭一个最小后端代理（Node + Express 或一个 Serverless 函数）：前端 → 你的 /api/chat → 模型，Key 只存在后端 .env
  4. 前端写一个最简单的输入框 + 按钮 + 显示回答

✅ 验收标准 ​

  • [ ] 能不看文档说清楚 system / user / assistant 各自的作用
  • [ ] 能手写一个不带任何 SDK 的 fetch 请求并调通
  • [ ] 你的前端代码里搜不到 API Key
  • [ ] 能看懂返回里的 usage，知道这次花了多少 token

模块二：提示词工程（第 1 周 · 后半） ​

🎯 学什么 ​

  • 提示词的标准结构：角色 + 任务 + 约束 + 输出格式 + 示例
  • 核心技巧：
    • Few-shot（给几个例子，模型照着学）
    • 思维链 CoT（让它"一步步想"，复杂任务质量飙升）
    • 分隔符（用 ``` 或 XML 标签把"用户数据"和"你的指令"隔开）
  • 结构化输出：让模型稳定返回 JSON，前端能直接 JSON.parse 消费（这是前端最实用的一招）
  • 提示注入（Prompt Injection）是什么，怎么防

💻 动手 ​

  1. 选一个真实任务，比如"把一段用户评论分类（正面/负面/中性）并提取关键词，返回 JSON"
  2. 先写一版烂提示词，看它输出多不稳定
  3. 逐步加：角色设定 → 输出格式约束 → Few-shot 示例 → 要求纯 JSON
  4. 把它接到模块一的代理上，前端能展示解析后的结构化结果

✅ 验收标准 ​

  • [ ] 同一个任务跑 10 次，输出格式稳定可被 JSON.parse
  • [ ] 能说出 Few-shot 和 CoT 分别适合什么场景
  • [ ] 能写一个 System Prompt，让模型稳定扮演某个角色不跑偏
  • [ ] 知道如何用分隔符防止用户输入"越权"改变指令

模块三：流式响应（第 2 周 · 前半）—— 前端核心战场 ​

🎯 学什么 ​

  • 为什么要流式：不流式要等十几秒才出整段；流式像打字机，首字 0.5 秒就来
  • 后端：请求加 stream: true，返回变成 SSE（text/event-stream），一行行 data: {...}，最后 data: [DONE]
  • 前端：用 fetch + response.body.getReader() + TextDecoder 逐块读取拼接
    • ⚠️ 不要用老的 EventSource，它只支持 GET、不能带 body
  • 工程细节：用 AbortController 做"停止生成"、错误处理、Markdown 增量渲染

💻 动手 ​

  1. 把模块一的后端代理改成流式转发
  2. 前端用 ReadableStream 逐字渲染，做出打字机效果
  3. 加一个"停止"按钮（AbortController）
  4. （进阶）了解 Vercel AI SDK 的 useChat，看它怎么把这套封装掉——理解原理后再用轮子

✅ 验收标准 ​

  • [ ] 能不靠任何库，纯 fetch + ReadableStream 实现打字机效果
  • [ ] 能解释 SSE 数据格式，知道 data: [DONE] 的作用
  • [ ] "停止生成"按钮能真正中断请求
  • [ ] 能说清为什么前端流式不用 EventSource

模块四：Function Calling（第 2 周 · 后半）—— 让模型动手 ​

🎯 学什么 ​

  • 模型本身只会"说话"，Function Calling 让它能"决定调用哪个函数、传什么参数"
  • 完整闭环：
    1. 你用 JSON Schema 描述工具（name / description / parameters）
    2. 模型返回 tool_calls（它想调哪个工具、参数是什么）
    3. 你的代码真正执行这个函数
    4. 把执行结果塞回 messages，再请求一次
    5. 模型基于结果给出最终回答
  • 关键认知：模型只负责"决策调用"，真正执行永远是你的代码

💻 动手 ​

  1. 定义 2-3 个工具：比如 getWeather(city)、search(query)、calculate(expr)
  2. 写完整闭环：发请求 → 拿到 tool_calls → 本地执行 → 结果回注 → 再请求 → 拿最终答案
  3. 加错误兜底：工具执行失败时返回结构化错误，而不是崩

✅ 验收标准 ​

  • [ ] 能从空白文件写出一个工具的 JSON Schema
  • [ ] 能完整跑通"请求 → tool_calls → 执行 → 回注 → 最终答案"
  • [ ] 问"北京天气怎么样"时，模型能正确选中 getWeather 并填对参数
  • [ ] 工具抛错时整个流程不崩，能优雅返回

模块五：Agent 开发（第 3 周 · 前半）—— 让模型自主编排 ​

🎯 学什么 ​

  • Agent = LLM 大脑 + 工具 + 循环 + 记忆。和单次调用的本质区别：它会自己多步决策直到完成任务
  • ReAct 循环：Thought（想）→ Action（调工具）→ Observation（看结果）→ 再想……直到得出答案
  • 工程要点：最大步数限制（防死循环）、每步日志追踪
  • 记忆：短期（对话历史 + token 窗口截断）、长期（对话结束提炼关键信息持久化）
  • 把模块三的流式用上：把 Agent 的每一步实时推给前端可视化

💻 动手 ​

  1. 在模块四的工具基础上，写一个 while 主循环（ReAct，最大步数 6）
  2. 加记忆：对话历史管理 + 简单的长期记忆（存 JSON）
  3. 前端可视化 Agent 每一步：💭 思考 → 🔧 调用工具 → ✅ 观察结果 → 📝 最终回答

✅ 验收标准 ​

  • [ ] 能讲清 Agent 和"单次 LLM 调用"的本质区别
  • [ ] 你的 Agent 能自己决定调用 2 个以上工具完成一个复合任务
  • [ ] 有最大步数限制，不会死循环
  • [ ] 前端能看到 Agent 每一步的执行过程

模块六：AI 编程工具 / Codex（贯穿全程 + 第 3 周 · 后半专项） ​

🎯 学什么 ​

  • 这类工具（Codex / Claude Code / Cursor）本质就是模块五学的那种 Agent，只不过工具是"读写文件、跑命令"
  • 不是让它替你写，是让它放大你：你定方向、做判断，它干重复劳动
  • 高效用法（决定成败）：
    • 给足上下文（贴文件、贴报错、说清意图），而非"帮我写个功能"
    • 让它先出计划再动手，你 review 通过再让它写
    • 让它干：写测试、补类型、重构、写文档、解释陌生代码
    • 用规则文件（如 CLAUDE.md）固化项目规范，让产出符合你的风格
  • 质量底线：AI 写的代码必须你自己看懂再合并，让它解释为什么这么写

💻 动手 ​

  • 从模块一开始，本计划的所有代码都用 AI 工具配合你写——边学边用就是最好的练习
  • Week 6 专项：用 AI 工具完成综合项目里你最不熟的部分，记录哪些提示有效、哪些翻车

✅ 验收标准 ​

  • [ ] 日常开发已习惯用 AI 工具，能明显感到提速
  • [ ] 能写出让 AI 一次到位的高质量提示（带上下文、带约束）
  • [ ] 不会无脑合并——能识别并修正 AI 写错的地方
  • [ ] 写出一篇"我的 AI 编程工作流"笔记
